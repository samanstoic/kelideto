# مدیریت و چرخش اعتبارنامه‌ها

## اصول

- اسرار در `.env` محلی، secret manager یا محیط اجرایی مجاز نگهداری شوند؛ هرگز در Git، issue، log، analytics یا artifact عمومی ثبت نشوند.
- هر محیط و هر ارائه‌دهنده credential مستقل داشته باشد. اعتبارنامه‌های افشاشده فوراً revoke شوند؛ صرفاً تولید مقدار جدید کافی نیست.
- دسترسی secret manager محدود، قابل‌ممیزی و برای مسئولان تعیین‌شده باشد. برای سرویس‌های پشتیبانی‌شده از کوتاه‌ترین عمر و کمترین مجوز ممکن استفاده شود.
- قبل از هر چرخش، مالک، وابستگی‌ها، روش rollback، اثر بر درخواست‌های درحال‌اجرا و معیار صحت را ثبت کنید.

## رویهٔ چرخش عمومی

1. رخداد/تغییر برنامه‌ریزی‌شده و مالک را ثبت کنید؛ نسخهٔ جدید credential را در secret manager بسازید.
2. اگر ارائه‌دهنده اجازه می‌دهد، بازهٔ کوتاه هم‌زیستی مقدار قبلی/جدید را فقط برای rollout کنترل‌شده فعال کنید.
3. secret جدید را با کانال امن وارد محیط کنید؛ فایل یا command line قابل‌مشاهدهٔ عمومی نسازید.
4. سرویس را reload/deploy کنید و اتصال را با health check یا تست رسمی کم‌خطر بسنجید؛ خروجی نباید مقدار credential را بازتاب دهد.
5. credential قبلی را revoke کنید، session/tokenهای وابسته را باطل کنید و log/audit را برای استفادهٔ غیرمنتظره بررسی کنید.
6. نسخهٔ پشتیبان رمز‌شده را فقط طبق سیاست مصوب نگه دارید؛ مقدار قبلی را از log، فایل موقت و ابزارهای استقرار پاک‌سازی کنید.

## کلیدهای ویژه

- **توکن راه‌اندازی:** پس از پایان نصب، باطل یا از runtime حذف شود. در نصب مجدد فقط توکن تصادفی جدید با انقضای عملیاتی کوتاه و دسترسی محدود تولید شود.
- **SMS، Web Push و پرداخت:** credential قبلی در پنل رسمی ارائه‌دهنده revoke شود. adapter تا آزمون sandbox/سلامت موفق، connected اعلام نشود.
- **Sanctum tokens:** برای افشای حساب، tokenهای همان کاربر/دستگاه یا همهٔ توکن‌های کاربر revoke شوند؛ تغییر نقش/وضعیت در برنامه همهٔ tokenهای او را باطل می‌کند. در رخداد گسترده، برنامهٔ ابطال دسته‌ای و اطلاع‌رسانی داخلی لازم است.
- **`APP_KEY`:** این کلید ممکن است برای رمزگذاری دادهٔ برنامه، cookie/session و payloadها استفاده شود. آن را مانند یک password عادی rotate نکنید. پیش از تغییر، ciphertextهای موجود و قابلیت key rotation پشتیبانی‌شده در نسخهٔ Laravel/تکامل برنامه را بررسی و backup restore را تمرین کنید. اگر افشا شده، دامنهٔ اثر و امکان بازیابی را با مالک فنی/حریم خصوصی ارزیابی و تغییر را به‌عنوان رخداد ثبت کنید.
- **Database/Redis:** credential را در سرویس مقصد و برنامه با rollout هماهنگ تغییر دهید؛ پورت‌ها را عمومی منتشر نکنید و پس از تغییر اتصال را از شبکهٔ مجاز اعتبارسنجی کنید.

این رویه مدت نگهداری یا تعهد حقوقی برای اعلان رخداد تعیین نمی‌کند؛ آن موارد باید با بازار هدف و قرارداد ارائه‌دهنده تطبیق داده شوند.
